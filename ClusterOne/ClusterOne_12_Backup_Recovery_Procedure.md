# 1. Purpose and Principles

This procedure defines what is backed up, how often, where to, and — the part that actually matters — how to get it back.

Three principles govern everything below.

1. **A backup that has never been restored is not a backup.** A restore drill is performed at least once during the pilot, and quarterly thereafter.
2. **Configuration is recovered from Git, not from backup.** Every node is rebuilt by Ansible. Backups exist for *data*, which cannot be regenerated; configuration is regenerated by definition.
3. **Not everything is worth backing up.** Node-local scratch, the dataset cache, and container images built from public sources are deliberately excluded. Recording that decision prevents it from being mistaken for an oversight during an incident.

# 2. What Is Protected, and What Is Not

| Data | Location | Recoverable from | Frequency | RPO | RTO |
| --- | --- | --- | --- | --- | --- |
| User home directories | `/home` (rpool) | Backup | Nightly | 24 h | 1 h |
| Project data | `/projects` (tank) | Backup | Weekly | 7 days | 4 h |
| Slurm accounting database | MariaDB `slurm_acct_db` | `mysqldump` + snapshot | Nightly | 24 h | 1 h |
| Keycloak database | MariaDB `keycloak` | `mysqldump` | Nightly | 24 h | 1 h |
| Grafana dashboards | Grafana SQLite | JSON export to Git | On change | 0 | 30 min |
| Cluster configuration | Ansible repository | Git | On change | 0 | — (rebuild) |
| Container images | `/opt/apptainer` | Weekly backup + rebuildable from definitions | Weekly | 7 days | 2 h |
| Prometheus metrics | Prometheus TSDB | **Not backed up** | — | — | — |
| Loki logs | Loki store | **Not backed up** | — | — | — |
| Node-local scratch | `/scratch` | **Not backed up — by design** | — | — | — |
| Dataset cache | `/scratch/_datasets` | **Not backed up** — regenerated from `/datasets` | — | — | — |
| Curated datasets | `/datasets` | **Not backed up** — re-downloadable from source | — | — | — |

RPO is the maximum data loss tolerated; RTO is the target time to restore.

`/datasets` is not backed up because every dataset in it is re-downloadable from a public source. This is only true if provenance is recorded. **Every dataset admitted to `/datasets` must have a `SOURCE.md` file recording its origin URL, version, checksum and admission date.** Without that file, the dataset is not re-downloadable and the exclusion is invalid.

Users are told plainly that `/scratch` is wiped at job exit. This is stated in the user manual, in the job template, and at onboarding.

# 3. Backup Architecture

```
   c1-anchor
   +-------------------------------------------+
   |  rpool (NVMe mirror)   /home, MariaDB     |
   |  tank  (HDD RAIDZ2)    /projects,         |
   |                        /datasets,         |
   |                        /opt/apptainer,    |
   |                        /tank/backup       |
   +--------------------+----------------------+
                        |
             ZFS snapshot + mysqldump
                        |
                 /tank/backup  (on-anchor, fast restore)
                        |
                    rsync nightly
                        |
              Off-anchor destination
              (departmental file server or
               external disk rotated weekly)
```

**On-anchor backups alone are not sufficient.** They protect against accidental deletion, quota mistakes and database corruption — the common cases — but not against loss of the anchor node itself, which is the scenario that ends the project. The off-anchor copy is what makes the difference between an inconvenience and a restart.

If a departmental file server is not available, two external disks are rotated weekly and one is kept in a different room. This is a low-cost arrangement and there is no acceptable reason to skip it.

# 4. Backup Schedule

| Time | Job | Action |
| --- | --- | --- |
| 01:00 daily | `zfs snapshot rpool/home@daily-<date>` | Instant, space-efficient point-in-time copy |
| 01:10 daily | `mysqldump` of `slurm_acct_db` and `keycloak` | Consistent logical dump to `/tank/backup/db/` |
| 01:30 daily | `rsync` of `/tank/backup` to the off-anchor destination | Off-anchor copy |
| 02:00 Sunday | `zfs snapshot tank/projects@weekly-<date>` and `tank/apptainer@weekly-<date>` | Weekly project and image copy |
| 03:00 Sunday | Snapshot pruning | Enforce the retention policy in §5 |
| 04:00 Sunday | Backup verification | Checksum the newest dump and confirm the off-anchor copy is current |

All jobs are deployed as systemd timers by the `nfs_server` Ansible role. Each writes a success or failure metric that Prometheus scrapes.

**A failed backup must be an alert, not a log entry.** `BackupFailed` (no successful run in 26 hours) and `BackupStale` (off-anchor copy older than 48 hours) are Alertmanager rules with runbook pages, on the same footing as `NodeDown`.

# 5. Retention

| Backup | Retention |
| --- | --- |
| Daily `/home` snapshots | 14 days |
| Weekly `/home` snapshots | 8 weeks |
| Weekly `/projects` snapshots | 8 weeks |
| Monthly `/projects` snapshots | 6 months |
| Database dumps | 30 daily, plus one per month for 12 months |
| Off-anchor copy | Mirrors the current on-anchor set |

Database dumps are retained for twelve months at monthly granularity because the accounting history is the evidence base for the Phase 2 proposal. Losing it does not stop the cluster, but it removes the project's ability to justify its own continuation.

# 6. Reference Commands

```bash
# --- Snapshots ---
zfs snapshot rpool/home@daily-$(date +%F)
zfs snapshot tank/projects@weekly-$(date +%F)
zfs list -t snapshot -o name,used,creation

# --- Database dumps ---
mysqldump --single-transaction --routines --events \
  slurm_acct_db | gzip > /tank/backup/db/slurm_acct_db-$(date +%F).sql.gz
mysqldump --single-transaction keycloak \
  | gzip > /tank/backup/db/keycloak-$(date +%F).sql.gz

# --- Off-anchor copy ---
rsync -aH --delete /tank/backup/ backup-host:/clusterone/

# --- Grafana dashboards to Git ---
# exported via the Grafana API and committed by the monitoring_server role
```

Credentials for `mysqldump` come from Ansible Vault. No credentials appear in a script, in Git plaintext, or in a shell history.

# 7. Recovery Procedures

## 7.1 Single user file or directory

The most common request by a wide margin. It requires no downtime and no administrator escalation beyond a check that the requester owns the data.

```bash
zfs list -t snapshot -o name,creation rpool/home
cp -a /home/.zfs/snapshot/daily-2026-09-14/<user>/<path> \
      /home/<user>/<path>.restored
chown -R <user>:<group> /home/<user>/<path>.restored
```

Restore to a `.restored` path and let the user confirm the contents before anything is overwritten. Overwriting the live copy directly turns one lost file into two.

## 7.2 Project directory

```bash
zfs list -t snapshot tank/projects
cp -a /projects/.zfs/snapshot/weekly-2026-09-08/<proj>/<path> \
      /projects/<proj>/<path>.restored
```

Notify every member of the project group before restoring shared data — another member may be mid-edit.

## 7.3 Slurm accounting database

```bash
systemctl stop slurmctld slurmdbd
mysql -e "DROP DATABASE slurm_acct_db; CREATE DATABASE slurm_acct_db;"
gunzip -c /tank/backup/db/slurm_acct_db-2026-09-14.sql.gz | mysql slurm_acct_db
systemctl start slurmdbd
sleep 10
systemctl start slurmctld
sacctmgr show cluster            # must list clusterone
sacct -S 2026-09-01 | head       # confirm history is present
```

Stop `slurmctld` before `slurmdbd`, and start them in the reverse order. Jobs already running continue; the controller reconnects to them on restart.

## 7.4 Grafana

Dashboards are recovered from the JSON exports in Git, not from the SQLite file:

```bash
ansible-playbook -i inventory/pilot.yml playbooks/anchor.yml --tags monitoring_server
```

## 7.5 Compute node

A compute node is never restored from backup. It is rebuilt.

```bash
scontrol update NodeName=c1-gpu03 State=DRAIN Reason="rebuild"
# reimage: Ubuntu 24.04, VLAN 20 address, SSH key
ansible-playbook -i inventory/pilot.yml playbooks/rebuild-node.yml --limit c1-gpu03
srun -p gpu -w c1-gpu03 --gres=gpu:1 apptainer exec --nv \
  /opt/apptainer/images/pytorch.sif \
  python -c "import torch; print(torch.cuda.is_available())"
scontrol update NodeName=c1-gpu03 State=RESUME
```

Target: under two hours, performed by a second operator without the original builder present. This is pilot exit criterion 6 and is tested and timed in week 12.

## 7.6 Anchor node — full disaster recovery

The worst case. Recovery order matters, because each step depends on the one before it.

```
 1. Provision replacement hardware; install Ubuntu 24.04 LTS
 2. Configure both VLAN interfaces (10.20.0.10 on VLAN 20)
 3. Import or recreate the ZFS pools
        zpool import rpool ; zpool import tank
        (if the disks are lost: recreate the pools per the
         Installation & Deployment Guide, then restore from
         the off-anchor copy)
 4. Restore /tank/backup from the off-anchor destination
 5. Run: ansible-playbook playbooks/anchor.yml
 6. Restore slurm_acct_db and keycloak from the newest dumps (§7.3)
 7. Restore /home and /projects from the newest snapshots
 8. Verify: exportfs -v ; systemctl status slurmctld slurmdbd mariadb
 9. Bring compute nodes back:
        ansible-playbook playbooks/compute.yml
        scontrol update NodeName=c1-gpu[01-06] State=RESUME
10. Run the deployment verification checklist in full
11. Announce restoration; publish an incident record
```

Target RTO for full anchor recovery is **one working day**, assuming replacement hardware is available. Hardware lead time is the dominant term and is outside the operations team's control — which is the argument for the anchor node being a purchase with a support contract rather than a repurposed desktop.

# 8. Restore Drill

Performed once during the pilot and quarterly thereafter. Announced in advance, timed, and documented.

| Step | Action | Pass criterion |
| --- | --- | --- |
| 1 | Restore a user file from a daily snapshot | Contents match the original |
| 2 | Restore a project directory from a weekly snapshot | Contents and ownership correct |
| 3 | Restore `slurm_acct_db` into a scratch database and query it | Job history present and queryable |
| 4 | Rebuild a compute node from Ansible | In service in under 2 hours, second operator |
| 5 | Verify the off-anchor copy is current and readable | Newest dump present and its checksum matches |

Each drill produces a dated record naming the operator, the elapsed time, and any documentation defect found. **If a drill fails, the documentation is wrong — correct this procedure, not the drill.**

# 9. Failure Scenarios and Response

| Scenario | Impact | Response |
| --- | --- | --- |
| Single disk failure in a pool | None (RAID1 / RAIDZ2 tolerate it) | Replace the disk; `zpool replace`; verify resilver completes |
| Two disks fail in `tank` | Pool at risk; a third failure loses it | Stop writes, replace immediately, prepare to restore from off-anchor copy |
| User deletes their own files | One user affected | §7.1 |
| Accounting database corruption | No new jobs accounted | §7.3 |
| Anchor node failure | Full outage | §7.6 |
| Compute node failure | Reduced capacity; queued jobs wait | Drain, repair, rebuild (§7.5) |
| Backup job fails silently | Backups stale, discovered during an incident | Prevented by the `BackupFailed` and `BackupStale` alerts |
| Off-anchor destination unavailable | On-anchor backups only; anchor loss becomes unrecoverable | `BackupStale` alert; treat as S2 and fix the same working day |
| Grid outage | Anchor on UPS; compute nodes lose power | Jobs resume from checkpoints; requeue affected jobs |
| Ransomware or destructive compromise | Potentially all live data | Isolate, restore from the off-anchor copy, rebuild every node from Ansible |
